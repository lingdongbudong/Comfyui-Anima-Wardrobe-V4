> 按**五级档位**（sfw / suggestive / explicit / hardcore / extreme）分级管理，低档绝不越界。
> 下载与安装即视为你已达到所在地区的法定年龄、并知悉插件包含此类内容。

> **当前版本 v4.0.0**
>
> ANIMA3 提示词随机生成插件 —— 按五级 NSFW 档位随机组合一段完整正文，
> 直接喂给 `Anima_工作流V3` 的「全局正文」节点。

零第三方依赖（纯 Python + 原生前端 JS）。与 `Comfyui-Anima-Wardrobe`（造型台 v2.x）
**可以同时安装**：类名、分类、HTTP 路由、前端脚本全部独立命名。

## 一、它解决什么

源脚本 `ANIMA提示词生成器.html` 是个浏览器单文件工具，靠「复制 → 粘贴进 ComfyUI
节点 1004」或「存成 prompts.txt」进入流程。它有 90% 的资产可以直接搬，但有三个硬缺口：

| 缺口 | 源脚本现状 | 本插件 |
|---|---|---|
| 没有分级 | 只有 `SFW` / `NSFW` 两个按钮，一刀切 | **五级闸门**，逐级放开段落；低档绝不越界 |
| 盲抽后补锅 | `Math.random()<0.65` 先抽，抽完才打补丁，高档内容会漏进低档 | 候选池**先按档位收敛**，抽完再体检、超档回滚 |
| 权重不可调 | 一个写死的概率 | **三层权重**：段 / 字段 / 选项，0 = 关闭，3.0 = 必现 |
| 结果出不去 | 只留在浏览器 | STRING 直出，可复现、可批量、可审计 |

## 二、快速开始

```bash
# 1. 插件放进 custom_nodes（没有依赖要装）
#    重启 ComfyUI

# 2. 用仓库里的示例工作流试跑
#    workflows/ → Anima工作流-29B-8步.json（另三个按 步数/底模 命名）
#    出图需要对应的底模 checkpoint（文件名即模型名，需自行下载）；
#    只想看提示词生成效果的话，节点上的「⚙ 打开随机面板」即可预览，不用跑图

# 3. 接进你自己的出图工作流
#    workflows/ 里的示例已内嵌「Anima 提示词随机生成（V4）」；
#    或手动：拖入「Anima 提示词随机生成（V4）」，把 text 输出
#    连到 CR Text 节点 1004（全局正文）那个**空着的 text 输入端口**。
```

接上去之后六条底模流自动全部吃到，工作流**一根线都不用改**；拔掉线就回到手写文本框。

## 四、NSFW 分级标准（核心）

沿用造型台已有的 **0–4 五级标度**，与 `AnimaNSFWGrader` 逐字对齐（有对拍测试钉住），
另加一个 `不限`。数值越大越露骨，低档**先从候选池里排除**，不是抽完再筛。

| 档 | key | 判定口径（画面里能看到什么） | 放开的内容 |
|---|---|---|---|
| **0** | `sfw` | 无任何暴露向内容 | ①–⑩ 段；⑥服装 / ⑦姿势 限安全子集 |
| **1** | `suggestive` | 有暗示但不露 | 微距泳装 · 高开叉 · 镂空裁剪 · 露肩 · 短裙 · 内衣轮廓 · 湿度质感 |
| **2** | `explicit` | 明显裸露或透视 | 全裸 / 上裸 / 透视真露 / 乳头 / 私处 / 内衣外露 / 半脱 · 法典场景 c1–c4、c7 |
| **3** | `hardcore` | 性行为 / 性道具 / 体液 / 束缚调教 | ⑫体位与性行为段 + ⑬特殊主题段 · 法典场景 c5、c6、c8、c10–c12、c14 |
| **4** | `extreme` | 群体 · 极端插入扩张 · 极端拘束装置 · 极限体液 | 群体多人 / 双管齐下 / 悬挂拘束 / 过量精液 等分类 · 法典场景 c9、c13 |

### 档位是怎么算出来的

三层叠加，顺序不能反：

```
最终档位 = max(判定表逐标签结果, 所在段的段下限, 逐选项上抬表)   →   再经人工校准表下调
```

- **判定表**：`anima_v4_nsfw.py`，从造型台 `wardrobe_rules.py` **逐字切片**而来，
  33 个常量 + 函数全部源码级对拍（`tests/check_nsfw_parity.py`）。
- **段下限**：`anima_v4_overrides.SECTION_FLOOR`。⑪⑫⑬⑭ 是 NSFW 专用段，
  段内任何内容都不应出现在低档。**只升不降**。
  没有它就会漏：判定表只看标签、看不到字段，`clitoris`（阴蒂）、`after sex`（事后余韵）、
  `red velvet` 这类词不在表里 → 判 0 档 → SFW 档把它们抽出来。
- **逐选项上抬**（v3.8.0 新增）：`anima_v4_overrides.LEVEL_RAISE`，**只升不降**，
  精确到 (字段, 选项) 且必须写理由。补的是"判定表**没收录**这个词"的盲区 ——
  例如第一人称视角扩展词条里的 `pov crotch`（判定表只认 `crotch cut`，单写 `crotch` 判 0）、
  `pov breasts` / `pov legs`。没有它，SFW 档会把「第一人称下体视角」抽出来。
  ⚠️ 能被判定表正确判定的**不要**登记在这里（如 `pov, fellatio` 由 `fellatio` 直接判 3 档）。
- **人工校准下调**：`anima_v4_overrides.LEVEL_DEMOTE`，**只降不升**，同样精确到
  (字段, 选项) 且必须写理由。目前只有 2 条（`wet hair` 系列：判定表的 `^wet `
  模式本意是抓 `wet clothes`，在「头发」段属于误命中）。

> ⚠️ 两张校准表的 (字段, 选项) 集合**不相交**，且有基线钉住
> （`tests/check_v3_repair.py` ⑥）；选项原文写错字段名会**静默失效**，也在同一处钉住。
>
> ⚠️ 哪一条在哪个档位能用，面板上按**段内是否还有 ≤ 当前档的选项**判定 ——
> 不用「段最高档」判。后者在段里混入分档词条后会误标（v3.8.0 给「视角」加了
> `pov crotch`(L2)、`pov, fellatio`(L3) 之后，⑧镜头段最高档被抬到 3，
> 全年龄档就会被打上「本档不参与」，而该段 16 条全年龄词条照样在抽）。

## 四之二、角色库与角色选择（v3.1.0 引入 · v3.2.0 起是**唯一**的角色入口）

> **v3.2.0 起「词库与权重」页不再提供角色权重。**
> 角色的选择完全由本页签接管（点卡片 = 抽取概率 100%）。
> **正文不写作品 IP 名**（v3.18.6）：选中/抽到 `hu tao, genshin impact` 时，正文只写 `hu tao`。
> 例外是**重名角色**（库里 109 组同名跨作品，如 `fubuki` 分属 3 部）——
> 那类保留完整 trigger，否则会被画成另一部作品里的同名角色。
> `state.role` 与报告里的 `role_full` 仍是完整 trigger（外貌对齐与自检 F10 靠它查表）。
>
> 优先级：**手填角色 > 角色库已选 > 未选则按「人数构成」自动抽**。
> 这样出图必定有角色，也不会再出现「我明明点了角色，却被权重静默否决」。

### 未选角色时：人数组合决定角色数（v3.3.0）

没选任何角色时，**先由 `count`（人数构成）抽出一个组合，再按组合抽对应数量的女性角色**：

| 人数组合 | 抽几位女性 | 男性怎么办 |
|---|---|---|
| 单人少女 / 单人熟女 | 1 | — |
| **一男一女**（`1girl, 1boy, hetero`） | 1 | count 里的 `1boy` 承担 |
| **双女**（`2girls, yuri`） | 2 | — |
| **一女多男**（`1girl, multiple boys, group sex`） | 1 | count 里的 `multiple boys` 承担 |
| **多人群交**（`multiple girls, orgy`） | 3 | — |

- ⚠️ **男性只用通用标签**（`1boy` / `multiple boys`），**不指定具体是谁** ——
  角色库 2383 位**全是女性**，没有男性角色可指。这是刻意的口径。
- ⚠️ 组合本身受**档位闸门**约束：`双女`是 L2、`一女多男`/`多人群交`是 L4，
  所以低档抽不到它们（这是原有的分级，不是新加的）。
- ⚠️ 未选角色时**不改写**人数标签 —— 人数是抽出来的组合，角色只是填进角色位。
  早先版本在这里无条件改成 `1girl, solo`，把所有组合都压成了单人，那是 bug。

### 可玩角色白名单（v3.13.0）

safebooru 是按「这个作品下**所有** character tag」枚举的，里面混着 NPC / 杂兵 /
声骸 / 邦布 / 周本 BOSS。实测绝区零枚举出 **279** 个基础 tag，其中可玩角色
只有 **52** 位。

⚠️ **程序分不出来**：danbooru 把 NPC 与可玩角色**都标成 character 类**；
`1girl` / `1boy` 共现只能剔**男性**，区分不了「女性 NPC / 女性 BOSS」和
「可玩女性角色」（实测 `hecate`（BOSS）90% 1girl，比很多真角色还高）→ 只能维护名单。

| 作品 | 来源 | 条数 |

| 绝区零 / 崩坏：星穹铁道 / 胜利女神：妮姬 | **danbooru 官方「角色列表」wiki 页**的 *Playable characters* 区块 | **52 / 67 / 199** |

#### ⚠️ 四个踩出来的坑（动这条链路前必读）

**① 三家的角色 tag 在 danbooru 上大多 📌 不带作品后缀**

`ju_fufu` / `hoshimi_miyabi` / `claret_flint` 才是正牌，而
`ju_fufu_(zenless_zone_zero)` 只是个 **NPC 空壳**。光靠 `*(zenless_zone_zero)`
枚举**永远拿不到真角色**，枚举出来的全是空壳。所以 `fetch_work_tags()` 里
专门加了「按白名单直查」这条腿。

**② 去重逻辑会把正牌角色挤掉**

原去重规则是「同作品下存在 `xxx_(作品)` 就丢弃裸名 `xxx`」—— 对这三家**正好反了**
（裸名才是正牌）。加了白名单豁免。**这就是 v3.12.0 之前「最新角色一个都收不进来」的真因。**

**③ safebooru 的 `search[name]` 多参数只认最后一个**

`?search[name]=a&search[name]=b` **只返回 b**，前者静默丢数 → 白名单 tag 全变
「零人气」再被剔掉。只能一个个查（带磁盘缓存 + 并发）。

**④ 造型台的 `work` 是粗分类**

崩铁角色被塞进 `honkai (series)`，跟 `TARGET_SLUGS` 的 key 对不上 →
会**绕过白名单过滤**（实测 `pom-pom` 就是这么漏进来的）。`_allow_of()` 依次试
`tag 反查表` → `work` → `work_tag`，命中后还会把 `work` **修正**成规范作品名
（`bronya_rand` 就是这么归回崩铁的）。

- 作品**登记在表里** → 只收表里的 tag（外加 `FORM_VARIANTS` 的形态/皮肤）
- 作品**不在表里** → 保持原行为（全量收），**不影响其它 285 个作品**
- ⚠️ 只登记**女性**；男性一律不登记（`wise` / `dan_heng` / `anton_ivanov` 等）

### 中文名（v3.12.0 起一律简体）

中文名从 wiki 抓，而 wiki 的默认变体常常是**繁体**（实测 2879 条里 132 条带繁体字：
`龍驤` / `雪風` / `愛彌斯` / `卡提希婭`）。构建时统一过一遍 `to_simplified()`：

- 装了 `zhconv` 就全量转换；没装则退回**内置 167 字兜底表**（覆盖本库实际用到的字）
- 另有 `ZH_FIX` 人工校正表，压过所有来源 —— 因为 `pick_zh()` 偶尔会从 wiki 的别名
  列表里挑到**不是名字**的东西（实测 `iuno` / `augusta` 抓到过 "鸣潮日月组" 这种分类名，
  `sigrika` / `sanhua` 抓到过带作品名前缀的写法）

### 角色「形态」机制（v3.12.0）

danbooru 的变体 tag 一律写成 `角色_(名字)_(作品)`，**形态与皮肤写法完全一样**：

```
yangyang_(xuanling)_(wuthering_waves)        ← 3.5 三星→五星形态（要收）
changli_(laurel_nymph)_(wuthering_waves)     ← 限定皮肤（要收）
jane_doe_(zenless_zone_zero)_(swimsuit)      ← 同人换装变体（不要）
```

程序分不出来，所以 `build_characters.py` 里有一张**人工白名单** `FORM_VARIANTS`：

- 基础 tag 照收（`canonical_of` 过滤）→ 变体**只放行白名单里的**
- 白名单命中时，中文名用表里写的（wiki 抓不到这些形态名）
- ⚠️ **加新条目的规矩**：key 必须与 danbooru **一字不差**（含 `_(作品)` 后缀）；
  **男角色的变体不要加**（`male_rover_(perpetual_spark)` 就刻意没加）
- ⚠️ 一旦放开全局规则，288 个作品的历史换装/同人变体会**全部**涌进来
  （角色数 2879 → 4000+，大量污染）—— 所以**只走白名单，别动 `canonical_of`**

鸣潮当前登记 **19 条**：13 条官方异格（秧秧·玄翎 / 心·月狐+明照 / 艾梅斯三形态 /
赞妮·炎狱 / 德妮娅·崩解 / 散华·驱邪 / 琳奈·佣兵 / 弗洛洛·奥斯蒂娜 / 秧秧·鸟形态 /
女漂泊者·永焰）+ 6 条限定皮肤（千咲·蜜桃帕菲 / 琳奈·薄荷 / 珂莱塔·夏日 /
长离·桂冠宁芙 / 今汐·桃夭 / 茉宁·绒梦）。

### 角色浏览器（面板 → 「角色库」页签）

- **默认按人气排行**展示，卡片带缩略图 + 中文名 + 英文名 + 人气值
- **点作品 IP 一键筛选**该作品下所有角色（★ 标记的是保底收录的目标作品）
- **关键词搜索**：中文名 / 英文名 / tag / 作品名 都能搜
- **点卡片即选中**（抽取概率 100%），再点一次取消
- **🎲 按当前筛选随机抽角色**（v3.8.0）：候选池 = 当前的「作品筛选 + 关键词 + 收藏视图」
  结果；位数可选（1–6），抽到的角色**追加**进「已选角色」（与手动点卡片同一语义），
  想换一批先点「清除已选角色」。抽的是**角色 tag**，而 `selected_roles` 随工作流保存
  → **"抽到谁"是可复现的**，所以这个功能不新增任何节点控件、不需要工作流迁移脚本
- **🔁 随机池**（v3.10.0）：把作品 IP 加进池子，**每跑一次自动换人**。见下节

### 两种模式：抽一次固定 vs 每次自动换（v3.10.0）

角色的两条路径**语义不同**，面板上分成两块，不要混：

| | 🎲 抽一次就固定 | 🔁 随机池（每次自动换） |
|---|---|---|
| 落到哪个控件 | `selected_roles` | `role_works` |
| 语义 | **这一次出图要用的角色** | **从哪个作品范围里每次重新抽** |
| 什么时候抽 | 你点 🎲 的那一刻（面板里） | **每次运行**（引擎里） |
| 换人 | 不换，除非你再点一次 | `seed = -1`（默认）时**每次排队都换** |
| 可复现 | 天然可复现 | 固定 `seed >= 0` 时同样逐字节可复现 |
| 怎么用 | 点作品筛选 → 点卡片 / 🎲 抽 | 点作品筛选 → **＋ 加入随机池**（可加多个） |

**优先级**（自上而下，先命中者胜）：① `force_role` 手填 → ② `selected_roles` 已选
→ ③ `role_works` 随机池 → ④ 全库随机。①② 是"用户显式指定"（写进 `role` 字段、
会改写人数标签）；③④ 是"自动随机"（**不改写**人数标签，人数由 `count` 组合决定）。

面板上如果同时有「已选角色」和「随机池」，会明确提示**已选角色优先** —— 否则用户会
以为"我加了池子它却不换人"。

**随机池认三种写法**：作品 slug（`zenless_zone_zero`）、英文名（`zenless zone zero`）、
中文名（`绝区零`）；多个用 `|` 或逗号分隔。**认不出的写法不会报错**，只在报告里提示
（老工作流里可能是别的写法，报错会让整张图跑不起来）；池子在该档位下为空时**回退全库**
并写明原因 —— 绝不静默回退。

> ⚠️ 池子**只从角色库（2383 位）里取** —— 与面板的作品筛选同一口径。源 HTML 里那
> 221 条角色若不在角色库里（构建时被剔掉的男性 / 非女性判定），就没有作品归属，
> IP 过滤时会排除在外（全库随机时仍可抽到）。
>
> ⚠️ **抽取是纯随机、不做"避免连续重复"**：池子几十到两百多人时，相邻两次抽到
> 同一位的概率 = 1/池大小（正常可接受）。要绝对不重复就得记录上一次结果到用户数据里，
> 代价是破坏"同 seed 同结果"这条承诺 —— 不值当。
>
> ⚠️ **动了控件个数**：`role_works` 是第 13 个控件，老工作流请跑一次
> `python tools/fix_workflows_v303.py --dry` 看影响面，再决定是否 `--inplace`。
- **已选角色以 chips 展示**，可单独移除，也可「清除已选角色」一键清空
- **卡片右下角 ✎ 编辑**、**顶部 ＋ 添加角色** —— 见「四之五、角色编辑与自定义角色」
- 缩略图加载失败时退化成**首字母色块**，不会留破图、也不会卡住浏览

> ⚠️ **预演与实跑现在完全一致**（v3.8.0 修）：面板的「🎲 全部随机（预演）」过去
> **没把 `selected_roles` / `lock_fields` 发给后端**，于是"选了角色点预演"看到的是
> 全库随机抽的结果，而真正跑工作流按已选角色走 —— 两边对不上。
> 现在这两个字段一起发，与「面板与工作流共用同一套引擎」的承诺对齐。

### 选中角色 → 人数标签自动联动

| 选中数 | 档位 ≤ 擦边 | 档位 ≥ 成人 |
|---|---|---|
| 1 位 | `1girl, solo` | `1girl, solo` |
| 2 位 | `2girls, multiple girls` | `2girls, yuri` |
| 3 位以上 | `multiple girls`（多人群像） | `multiple girls`（多人群像） |

> ⚠️ **为什么双人要看档位**：`yuri` 在判定表里是 **2 档**内容（「百合」分类）。
> 全年龄/擦边档写 yuri 会凭空越档 —— 那是本插件最核心的承诺。
> 所以低档用中性的 `2girls, multiple girls`。

三条硬规矩：

1. **选中即 100% 抽取**，且**不受权重影响** —— 用户显式点了角色，这一条压过
   「字段权重 0」。真不想用就点「清除已选角色」。
2. **2 位以上不做外貌对齐**：两个人各有各的官方发色，强行对齐其中一位是错的
   （角色 tag 本身已经带足特征）。
3. **2 位以上会清空单人向的 NSFW 字段**（体位 / 高潮 / 体液 / 特殊主题），
   否则会出现「一个人摆着双人体位」的自相矛盾。

## 四之三、收藏（⭐）

收藏是**长期标记**，与「已选角色」是两个独立维度：

| | 收藏 ⭐ | 已选角色 |
|---|---|---|
| 含义 | 我常想用的角色 | 这一次出图要用的角色 |
| 保留在哪 | 插件目录（跨会话） | 工作流 JSON |
| 是否影响出图 | 不直接影响 | 直接决定 |

- 每张角色卡片**右上角**有 ⭐ / ☆，点一下收藏、再点取消
- 作品列表顶部有「**⭐ 我的收藏 (N)**」一行，与「全部作品」并列，点它只看收藏
- 收藏为空时该行置灰，点进去给明确空状态提示
- 收藏存在 `presets/user_favorites.json` —— 可备份、可随插件分享
- ⚠️ 点 ⭐ **不会**顺带把角色选中（已 `stopPropagation`）

## 四之四、预设（保存 / 一键恢复）

把当前这一整套配置存下来，随时切回去。

- **存什么**：档位 + 三层权重 + 段开关 + 已选角色 + 标签上限 + 基准抽取概率
  + 外貌对齐 + 手写补句 + 手填角色
- **不存 seed**：seed 代表"复现某一条预览"，是一次性的；存进预设会让
  「加载预设」变成「每次都出同一张」，那不是这个功能该有的语义
- **入口**：右列「设置」区下方的「预设」小节 ——
  下拉选择 + 📥 应用 / 🗑 删除（两步确认）/ 输入名称 + 💾 保存当前配置
- **存在哪**：`presets/user_presets.json` —— 可备份、可随插件分享给别人
- ⚠️ 读请求可能比写操作**更晚**返回、且带的是旧快照 → 写操作会作废在途的读。
  不设防的话会出现「删掉的预设又冒出来」（冒烟抓到过）

## 四之五、角色编辑与自定义角色（v3.4.0）

角色库不再只读：内置角色可以改，也可以添加自己的角色。

### 为什么另存一层，而不是直接改角色库文件

`presets/anima_v4_characters.json`（2383 位）是 `tools/build_characters.py` 的
**联网重建产物** —— 重跑一次就把手改内容全冲掉。所以用户的新增/编辑一律落在：

| 文件 / 目录 | 存什么 |
|---|---|
| `presets/user_characters.json` | `edits`（按内置 tag 的字段覆盖）+ `custom`（自定义角色整条记录） |
| `presets/user_thumbs/` | 用户上传的预览图（**刻意与 `presets/thumbs/` 分开**：抓图脚本会遍历 `thumbs/` 清理不合格图，用户图放那儿会被误删） |

合并顺序：**内置 2383 → 套用 edits → 追加 custom**，且会**重算 `works.count`**。
三个消费方同时看到合并结果：面板 `/characters`、`role` 随机候选池、外貌自动对齐。

> **随仓库发布说明**：本仓库自带的 `user_characters.json` 预填了 122 条角色资料修正
> （上游 wiki 的脏数据，如 emilia 的 trigger 被误写）与 12 位补充角色（无职转生等）。
> 这是**数据资产**，保证你开箱拿到的角色库与作者实机一致、测试全绿；
> 你在面板里的后续编辑会继续追加到这个文件，不会被冲掉。
> 你的收藏与命名预设（`user_favorites` / `user_presets` / `user_scene_favorites`）
> 则是纯个人数据，不在仓库内，首次运行自动创建。

### 能改什么

| 可改 | 说明 |
|---|---|
| **角色标签（trigger）** | 真正进提示词的那串（如 `hatsune miku, vocaloid`）。只收英文小写，≤120 字符 |
| **中文名** | 留空即回退内置值 |
| **作品** | 下拉现有作品，或直接输一个新的（会自动补一行作品） |
| **预览图** | 本地上传 PNG / JPG / WEBP（≤2MB，保存时缩到 160px） |
| **特征标签（tags）** | 角色的官方特征标签列表（如 `long hair` / `aqua eyes`）。逐行增删改 + 一键恢复内置（v3.5.0，见下） |

⚠️ **角色 tag（slug）不可改**：它是 `char_index` 的键、也是图片文件名，改它等于
"删掉再造一个"。已保存工作流里的 `selected_roles` 存的是 **tag**、靠 `char_index`
展开成 trigger —— 所以**改 trigger 不会让老工作流失效**，只改 tag 才会。

### 怎么用

- 每张卡片**右下角**有 **✎**：点开编辑弹窗（中文名 / 作品 / 角色标签 / 预览图 / 特征标签）
- 角色库顶部有 **「＋ 添加角色」**：新增自定义角色（添加后列表会自动筛选到它，
  不然新人气为 0 会沉到很后面）
- 自定义角色带**「自定义」角标**；弹窗里给 **🗑 删除角色**（两步确认）
- **内置角色也能删**（v3.18.6）：弹窗里给 **↺ 恢复默认** + **🗑 删除角色**；
  删除会把完整记录先写进 `presets/_retired/anima_v4_characters.removed.json`（tombstone，
  想找回就往里翻），再原子写回 `anima_v4_characters.json`。
  ⚠️ 重跑 `tools/build_characters.py` 会重建整个库 → 被删的会回来（那是刻意的）。
- **多选批量删除**（v3.18.6）：角色库顶部 **☑ 多选** → 点卡片是**勾选**（不会写入
  `selected_roles`，删角色不会顺手改你的提示词）→ 顶部出现 **🗑 删除所选（N）**，
  两步确认后一次删完；自定义与内置可以混选。
- ⚠️ 点 ✎ **不会**顺带把角色选中（已 `stopPropagation`，与 ⭐ 同款）

### 校验与上限

trigger 空 / 含大写 / 含中文 / 超长 → 前端与后端**都会拒**（前端拦是为了不让用户
白发一次请求，后端拒才是权威）；图片非 PNG·JPG·WEBP / 超 2MB 同样拒绝；
自定义角色上限 **500** 条。

> 编辑过的内置角色**不会**污染 `presets/anima_v4_characters.json` ——
> `tests/check_v3_userdata.py` 全程盯着这条（逐字节校验）。

### 特征标签（tags）怎么改（v3.5.0）

编辑弹窗底部的「特征标签」区：

- **看**：一行一条，展示的是**全量**标签（列表接口只带前 8 条，弹窗会按需拉
  `GET /characters/detail` 拿全）；头部显示「内置 N 条 · 已被修改」
- **增**：点「＋ 添加标签」加一行（空行不计入条数）
- **删**：点该行的 `×`
- **改**：直接改那一行的文字
- **一键还原**：「↩ 恢复内置标签」把行填回内置值；保存时若与内置**完全一致**
  就发空数组（= 不写覆盖），所以还原是真的把覆盖清掉、而不是存一份和内置一样的副本
- 一行里粘 `A, B` 会被自动拆成两条；大写会自动归一成小写（这点比 trigger 宽松）

**这些标签在引擎里只影响两件事**（`anima_v4_rules.appearance_for()`）：

| 用途 | 生效条件 |
|---|---|
| **体型（figure）** | 只认 5 个标签：`huge breasts` / `large breasts` / `medium breasts` / `small breasts` / `flat chest` —— **始终生效** |
| 兜底**发色 / 瞳色** | ⚠️ **仅当该角色没有 `hair`/`eyes` 记录时**才从标签里捞（2070/2383 已有该字段，所以对多数角色不生效） |

- **单个标签 ≤40 字符**：⚠️ 不是随便定的 —— `appearance_for()` 会跳过超过 40 字符的
  标签，**存了也不会生效**，所以直接拒绝并说明原因
- 最多 **40 条**；清空全部 = 恢复内置标签（与「中文名留空」同一套语义）

> ⚠️ 自定义角色的空标签是**真的没有标签**（它没有"内置值"可回退）——
> 这是有意的语义区别，见 `anima_v4_store.save_user_character`。

## 四之六、出图元数据里的提示词（v3.6.0 起，v3.7.0 修到位）

### 病在哪

出图后用看图工具看这张图，「正向提示词」只有 `masterpiece, best quality`（**质量词**），
真正的画面内容一个字都没有。解剖真实出图确认 —— **不是被截断，是正文压根没进元数据**：

| 节点 | 在元数据里的值 |
|---|---|
| `AnimaV4RandomPrompt`（插件） | 13 个控件值里**没有任何文本位**（正文预览是 `serialize:false` 的 DOM widget） |
| `CR Text`（承接插件输出） | `['']` ← 空串（text 是**连线**） |
| `StringConcatenate`「触发词+质量词 → 全局正文 拼接」 | `['', '', ', ']` ← 两段都空（都是连线） |
| `CLIPTextEncode`「正向条件（自动拼接）」 | `['']` ← 空串（text 是连线） |
| `StringConcatenate`「自动拼接：官方质量词（本流）+ 全局正文」 | `['masterpiece, best quality']` ← 链上唯一"有字"的 |

链路：`插件 → CR Text → StringConcatenate → CLIPTextEncode(正向) → 采样器 → 解码 → SaveImage`。
文本全程只在连线上流动，看图工具读不到，就退而取了链上唯一有字的质量词节点。

### ⭐ 看图工具到底读哪儿（v3.7.0 用对照实验问出来的）

v3.6.0 只是"把能写的地方都写上"，**没搞清看图工具读哪一份**，所以修完现象没变。
v3.7.0 直接对着工具自己的解析接口（`ComfyUIGallery` 的 `/api/inspect`）做**对照实验**，
逐个位置打唯一标记，看它跟着谁变 —— 结论很硬：

| 改动位置 | 工具显示是否跟着变 |
|---|---|
| `workflow` 里**正向上游 `StringConcatenate` 的 `widgets_values[0]`** | ✅ **跟着变** |
| `workflow` 里终点 `CLIPTextEncode.text` | ❌ 不变 |
| `workflow` 里 `CR Text.text` | ❌ 不变 |
| `prompt`（API JSON）任意字段 | ❌ 不变 |
| A1111 风格 `parameters` 块 | ❌ 不变 |
| 本插件的 `anima_v4_prompt` 块 | ❌ 不变 |

它甚至不是"挑一个"，而是把正向上游链路上**每个** `StringConcat` 的 `widgets_values[0]`
按「上游 → 下游」**拼起来**（给两个都打标记 → 显示 `A43A79`）。
而 Anima 工作流里"自动拼接"那个节点的 `string_a` 恰好只放着质量词 —— 这就是
`masterpiece, best quality` 的来源。

### 怎么修的（不改你的工作流）

`extra_data['extra_pnginfo']` 是**同一次执行里所有节点共享的同一个 dict**，而原生
SaveImage 是在**自己执行的那一刻**才把它序列化。所以插件节点在运行时把正文写进去，
SaveImage 就照常写进 PNG：

- ✅ **一根线都不用改**、不装额外节点、当次出图就生效
- ✅ 用的是 **hidden 输入**（`EXTRA_PNGINFO` / `PROMPT` / `UNIQUE_ID`）——
  不是控件、不占控件位 ⇒ **不需要工作流迁移脚本**，老工作流零影响
- ✅ 完全不影响出图结果（`workflow` 是 UI JSON，ComfyUI 从不拿它跑图）

写四个落点：

| 落点 | 写什么 | 为什么 |
|---|---|---|
| **承载位** —— `CR Text.text`、各「拼接」节点的 `string_b` | **正文原值** | 这些位置运行时的值就是插件正文 |
| **终点位** —— 6 个正向 `CLIPTextEncode.text` | **「该流质量词 + 正文」** | 这里运行时是 质量词+触发词+正文；触发词由 LoraManager 运行时给，插件拿不到 |
| **兜底位** —— 链上其它文本节点**空着**的文本位 | **正文原值** | 有些工具会读链上别的节点。⚠️ **只填空位，绝不覆盖用户写死的字面量** |
| **上游拼接位**（v3.7.0）—— 正向往上游链路上 `StringConcat` 里**已有字面量**的 `string_a` | **「该流质量词 + 正文」** | ⭐ 看图工具**实际读的就是这一位**。只改**原本非空**的；空的是连线位，写了会让工具拼出重复 |

另外往 `extra_pnginfo` 加一个专用键 → SaveImage 会照原生约定写成同名 **PNG tEXt 块**
`anima_v4_prompt`，内容是 JSON：

```jsonc
{
  "schema": "anima-v3/pngmeta@1", "plugin": "Comfyui-Anima-Wardrobe-V4", "version": "3.7.0",
  "positive": "<插件产出的正文原值>",
  "positive_full": "<尽力还原的完整正向 = 该流质量词 + 正文>",
  "negative": "<顺着采样器的 negative 输入**配对读回**的负向>",
  "written": 25, "workflow_ok": true
}
```

> ⚠️ **只对之后新出的图生效** —— 元数据是出图那一刻写进 PNG 的，老图已经定型。

### 安全边界（改这个模块前必读）

- `workflow`（UI JSON）**只用于展示** → 随便写；`prompt`（API 执行图）**就是拿去跑的那张图**
  → **只写未声明的惰性键** `anima_v4_prompt`。
- ⚠️ **绝不**把 `CLIPTextEncode.inputs.text` 从连线改成字面量 —— 那会丢掉第三方拼的前缀、**直接改坏出图**。
  宁可少写一个键，也不能改坏图。（`tests/check_v3_pngmeta.py` 里有一条断言盯着"已声明输入零改动"。）
- ⚠️ **幂等守卫**：`上游拼接位` 写进去的字面量**会被链路解析重新拼一遍**，所以
  "该位已含正文就跳过"是硬要求 —— 不然重复注入会写出 `质量词 + 正文 + 正文 + …` 越写越长。

1. **"一定出现"必须锁两个字段**：`socks`（丝袜值）+ `shoes`（玛丽珍 / 高跟 / 乐福 / 室内鞋 /

3. **`sock_color` 必须闭麦**（`drop_fields`）：候选值本身已带颜色（`black pantyhose`），

所以**别为了"更好看"往 L0 条目里塞擦边词**，那会把它顶出全年龄档。

### 它复用了什么（为什么不用新增控件）

场景搭配**就是**「法典场景」那套机制的扩展，两条来源共用一条链路：

```
pools.json 的法典 14 组 ─┐
                        ├─→ canon() 合并 → apply_preset() 填充 state → collect() 输出
anima_v4_scenes.json 33 ─┘
```

因此自动继承：**档位闸门**（超档的搭配在本档根本不在候选池里）·
**权重让路** · **锁定让路** · 加上 v3.8.0 的**成品自动修复**。

> ⚠️ 节点侧**没有任何"字段取值"控件** —— 字段值只能来自 随机 / 权重 /
> `force_role` / 预设。所以"把某组值固定下来"必须有个承载位，而
> `n_canon` 已经在权重表里有位置，复用它比新开一个控件干净得多：
> **零控件改动、零工作流迁移脚本**，而且状态随工作流保存。

### 三条硬规矩

1. **预设绝不写 `count` / `role`** —— 人数与角色是"地基"，由你点选（或按
   人数组合自动抽）决定。预设抢这两个字段会让「选了双女却只有 1 位角色」
   这类矛盾复现（v3.3.0 修过一次）。构建脚本会拦住这条。
2. **预设字段进「不可裁剪」名单** —— 标签数超限时按优先级裁剪，
   但预设写进去的字段**一个都不削**。否则"选了场景却少了一半"，
   「固定」就成了空话。
3. **预设 id 绝不进正文** —— `n_canon` 的值是内部主键（`c8` / `sc_xxx`），
   `collect()` 会跳过它（见 `_NO_EMIT_FIELDS`）。顺带修掉了一个 v3.0.0 起
   就存在的 bug：过去 32.5% 的 NSFW 正文末尾会带一个 `c1`…`c14` 垃圾 token。

```bash
# ① 编辑 presets/anima_v4_scenes.json（只写人写的内容：zh/desc/tags/extra）
# ② 校验 + 派生档位（会拦住写错的字段名与选项原文）
python tools/build_scenes.py
# ③ 基线
python tests/check_v3_scenes.py
```

`level` 由脚本**按内容派生**（`max(各字段值的准入档位, extra 各标签档位)`），
**不要手改** —— 它决定"这条搭配在哪些档位可用"，手写必然漂移。
`--check` 模式用于 CI：磁盘 JSON 与派生结果不一致就报错。

> ⚠️ **踩过的坑（写 extras 时注意）**：判定表有一批"看词不看语境"的口径，
> `wet ground` / `wet sand` / `wet wall` 会被 `^wet` 判成 **2 档**，
> `sheer curtain` 判 2 档，`unbuttoned collar` 判 1 档 —— 它们会把整条
> SFW 搭配顶到高档位、在全年龄档直接消失。写 extras 时避开这些词
> （用 `rain puddle` / `splashing water` / `damp wall`），
> 跑一次 `build_scenes.py` 就能看到每条的实际档位。

## 四之七之二、特写搭配（v3.18.0 起）

按**部位**取景的固定组合 —— 独立页签、**只允许手动套用**。与场景搭配共用同一条链路
（`n_canon → canon() → apply_preset()`），但两条硬隔离，一条都不混排。

- **入口**：面板第四个页签「🔍 特写搭配」，**62 条**，一级按**部位**分组
  （面部 8 · 眼与唇 4 · 上半身与胸 6 · 手 4 · 腿 **12** · 脚 4 · 臀 6 · **🔞 成人向 18**），
  顶部一条部位筛选（全部 / 面部 / …），档位只做卡片角标
- **🎭 角色来源（v3.18.2）**：面部 / 眼与唇 / 上半身与胸 三组保留角色，页顶给一条「角色来源」栏 ——
  **留空 = 全库随机；填作品 slug / 英文名（多个用 `|`）= 该 IP 内随机**；已选角色时优先用已选。
  它写的是**同一个** `role_works` 控件（与角色库「🔁 随机池」同一份数据），不是另开一套设置。
- **只手动**：每条带 `"manual_only": true` —— 随机候选池里**永远没有**它们，
  只有该选项权重顶到 **3.0**（面板点「套用」）才进候选。
  这样"抽卡时突然冒出个腿特写"不会发生，现有随机分布逐字节不变
- **收紧取景（v3.18.1，按部位分级）**：用户口径是「**特写只描述画面里能看见的东西**」，
  所以实现不是"关几个捣乱字段"，而是反过来按部位给一张**可见字段白名单**（`NEAR_VISIBLE`），
  白名单之外的字段一律权重 0（预设自己写进去的字段自动保留）：
  - **面部 / 眼与唇**：关 ④身材 ⑤妆容；保留 ②头发 ③五官 与**角色**（要的就是脸与表情）；
    看不见的 服装/鞋袜/姿势/动作/设备 全部清零 → 实测出"脸 + 肩 + 颈"
  - **上半身与胸**：只关 `figure` / `leg` 两项（保服装与姿势，否则会画成裸体）
  - **手 / 腿 / 脚 / 臀**：关 ②③④⑤ 段 + 清空角色并锁 `role`（局部特写不该有脸），
    只留 部位词/袜子/鞋/姿势/机位/景深/地点/光影 → 实测腿组出"头完全出画"的纯腿部特写
  取消套用（或换套另一条）时，段权重 / 字段权重 / 人数袋 / 角色三件套 / 锁定表全部原样还回；
  卡片带 `✂ 收紧取景`（+`🧹 清角色`）角标、状态栏明写，**不静默**
- **部位词走 `extra`**：`face / eyes / iris / eyelashes / thighs / knees / calves / ankles /
  feet / toes / soles` 等全部实测 **L0**，不进词库真源 → 零漂移对拍不受影响。
  ⚠️ 判定表对 `^wet` 一律判 2 档，所以湿脸写 `damp skin` 而不是 `wet face`（README 老坑）
- **档位**：L0 30 · L1 1（泪光 —— `emotion=tears` 词库里本来就是 L1）·
  L2 1（湿衣 —— `wet clothes` / `see-through` 判 2 档，按词库口径**保留原样**）
- **取景锚点（v3.18.1）**：腿 / 脚 / 臀 的 `extra` 统一追加
  `head out of frame` + `legs focus / feet focus` + `lower body`（实测同 seed 下，不加会退回全身照，
  加了才稳定"头出画"）；`ass`（臀部）另加 `ass focus`。四肢/臀**不放 `dof` 字段** ——
  它的候选里有 `focus on face`，与"只看局部"自相矛盾。
- **成人向组（v3.18.5，18 条）**：L1 4（胸沟俯视 / 情趣丝袜大腿 / 舌与唾液 / 足底）·
  L2 8（乳首 / 内裤 / 薄纱透视 / 大腿根 · **双女按摩胸部** / **双女口含乳头** ·
  **隔衣揉胸** / **贴胸搂抱**）· L3 5（四足跪姿后视 / 口交 / 舔阴 / 局部射精 · **双女吸乳吐舌**）·
  L4 1（**双女泌乳**）。
  双女共 6 条（`count_lock: "2girls, yuri"` + `role_ok`）。⚠️ **双女档位下限是 L2**：
  双女只能靠 count 的 `2girls, yuri`，而 `yuri` 本身判 L2 —— 即使写的是"隔衣揉胸"这种擦边内容，
  真实等级仍为 L2（自检 `real_level` 也是 2）。要真做 L1 双女，得改词库真源给 count 加 `2girls`。
  走极简，`figure` / `skin_detail` 留在可见白名单（胸型与肤质在画内），袜鞋只留预设自己写的。
- **成人向逐条分档（v3.18.3）**：其中**画框里看得见脸或头发**的 5 条打了 `role_ok`
  （口交 / 舔阴 / 舌与唾液 / 胸沟俯视 / 薄纱透视）—— 这 5 条**保留角色**（支持全库随机 / 限定作品 IP）
  与 ②头发 ③五官 段；其余 7 条仍清角色。卡片角标：`🎭 角色生效` vs `🧹 清角色`，一眼能分。
- **⚠️ 权重基线持久化（v3.18.5 修 bug）**：套用特写会把白名单外的字段权重设为 0，旧实现把这些
  「清零前的原值」只存在内存 `ui.nearRestore` —— **刷新 / 节点重开 / 换工作流就丢**，
  被清零的字段（`socks` / `shoes` / `outfit` …）永久停在 0，表现为「**腿部服装随机不生效**」
  （实测：`fields.socks=0` 时袜鞋 8/8 全无；干净权重 8/8 都出）。现在基线写进
  `weights_json._nearBase`（随工作流持久化），**每次套用前无条件先还原再清零** ——
  刷新后同样有效。`_nearBase` 是引擎忽略的额外键（`parse_weights` 只读 sections/fields/options）。
- **⚠️ role 锁定诊断（v3.18.4 修 bug）**：`lock_fields` 含 `role` 时引擎会**跳过自动抽角色**，
  只剩手填角色能出人 —— 而那个锁是套用无脸条目时写进节点控件的、会随工作流持久化，
  页面刷新后内存快照丢失就永久留着。现在：① 套用「要角色」的条目（面部 / 眼与唇 / 上半身与胸 /
  `role_ok` 成人向）时**自动摘掉**残留的 role 锁（快照记录，取消套用原样还回），状态栏明说；
  ② 特写页顶只要发现 role 被锁就显示**诊断行**（`⚠️ 随机角色与作品 IP 抽角色都不会生效`）+
  `🔓 解除 role 锁` 按钮，不必再猜。⚠️ 套用无脸条目时仍会临时锁 role（这是刻意的）。
- **双女条目（v3.18.3 / v3.18.4）**：舔阴特写、双女按摩胸部、双女口含乳头、双女吸乳吐舌、
  双女泌乳 = **双女**，预设自带 `count_lock: "2girls, yuri"`，
  套用时人数钉死为双女、`extra` 补 `yuri`，引擎按 `2girls` 自动抽**两位**角色
  （限定 IP 时两位都从该 IP 抽）。⚠️ 若已选角色不足 2 位，套用会**清空已选**并改走自动抽两位，
  状态栏写明原因（不会静默改）。
- **效果边界（v3.18.1 实测，已达标）**：面部 / 眼与唇 → **脸 + 肩**；上半身与胸 → 胸像；
  腿 / 脚 / 臀 → **纯局部**（头出画，正文只剩 16–21 个可见标签）。
  前提是"文字里没有画面外的东西"—— 这正是白名单机制要保证的。
- **⚠️ 取景闭麦 `drop_fields`（v3.22.0）**：条目可以**点名让某个字段彻底闭麦**
  （`"drop_fields": ["pose_base"]`）—— 套用时该字段权重 **0**，既不写值也不参与随机。
  为什么需要它：`pose_base` 光"不写进 `tags`"**不够** —— 它在「🔞 成人向·有脸」的
  可见白名单里，权重仍是 `1.0`，照样随机抽，抽到 `all fours` 一样把整具身体拉进画面。
  校验在 `tools/build_scenes.py`：字段必须真实存在、不得是 `count` / `role`、
  不得与 `tags` 里的同名字段并存（自相矛盾）。
- **口交特写 = 第一人称，女方只留脸与肩（v3.22.0 修）**：`viewpoint: pov, fellatio` ·
  `shot_size: close-up` · `dof: focus on face` · `eye_gaze: looking up` · `pose_base` 闭麦 ·
  `extra` = `solo focus, penis, face, shoulders, head and shoulders, saliva, lips, blush, looking up at viewer`。
  ⚠️ 四条实测结论：
  ① `pov, fellatio` 是**唯一**能同时给出"第一人称口交语义 + L3 档位"的选项
  （`saliva` / `tongue` / `open mouth` 全是 L0），所以它必须留；
  ② **`solo focus` 不能省** —— 它才是"镜头只对着她一个人"的那道闸，省掉时 4 张里 2 张跑出对方的手、1 张露胸；
  ③ **"只拍脸与肩"约束的是女方**：生殖器按用户口径**要在画面里**，所以 `penis` 是显式写进 `extra` 的
  （不靠 `pov` 标签碰运气），两条约束各管一段、互不冲突；
  ④ 旧配方里的 `kneeling` 是"冒出全身"的直接原因，改用闭麦而不是换成别的姿势值。
- **候选随机字段 `random_fields`（v3.22.0）**：条目可给某字段列几个候选
  （`"random_fields": {"mouth": [...], "emotion": [...]}`），**套用时抽一个** ——
  同一条特写每次的口部状态与表情都不同，而不是一条死配方。口交特写现在是
  **口部 5 态 × 表情 5 种**（张口 / 伸舌 / 微张 / 舔唇 / 咬唇 × 羞耻 / 含泪 / 兴奋 / 失神 / 惊讶）。
  三条实现要点：① 候选照样过档位 / 权重 / 锁定三道闸门（不是后门）；
  ② **候选彼此矛盾时会重抽**，不是像 `sanitize` 那样整字段清空 ——
  旧路径 12 抽里有 2 次 `mouth` 直接消失（`surprised` 禁 `biting own lip`、`expressionless` 禁 `open mouth`）；
  ③ **没有 `random_fields` 的条目一次 rng 都不消耗**，所以零漂移对拍（`check_v3_near` ④）仍然全等。
- **怎么加 / 改**：编辑 `presets/anima_v4_scenes.json`（`group: "near"` + `theme: 部位` +
  `manual_only: true`）→ `python tools/build_scenes.py` → `python tests/check_v3_near.py`

> ⚠️ 为什么必须隔离：`n_canon` 的默认字段权重是 `1.0`，**随机抽取本来就会命中场景预设**
> （实测 `draw(level='sfw', seed=9)` 直接套了 `sc_balcony_night`）。
> 新预设直接塞进同一个池子 = 改变现有随机分布，"不影响原行为"就成了空话。

### 面板怎么找

「🎬 场景搭配」页顶部多了一条筛选：**「全部」/「🧎 姿势场景」**。

卡片角标统一是 `【姿势·正座】` 这种格式，一眼能认出来。

**进**（与普通 SFW 场景一致）。所以抽卡时可能直接抽到「跪坐」并锁死姿势 ——
不想要这种行为时，把 `n_canon` 权重设为 `0`（或把该字段排除）即可，

### 加新姿势场景

① 不写 `count` / `role`（人数与角色是地基）；② `tags` 的值必须真实存在于词库
（写错 = 静默失效）；③ `level` 由脚本派生，手写必然漂移。

## 四之八、字段联动（v3.15.0）

在此之前，**所有字段都是各自独立随机**的 —— 于是会稳定地抽出各种自相矛盾的组合。
v3.15.0 加了一层联动，三张表都在 `anima_v4_link.py` 里（人工维护的语义知识，
与引擎逻辑分开，改表不用翻 2600 行的 rules.py）。

### ① 体位配对：`n_act` × `n_pos`

| 抽到 | 就不会再配 |
|---|---|
| 骑乘位 / 反向骑乘 / 颜骑 | **男上位**、弯腰撅臀、四肢着地、背贴墙壁 |
| 正常位 / 交尾压制 / 俯卧位 | **女上位**、跨坐、直立跨坐、蹲踞骑乘、四肢着地 |
| 俯卧位 | 还会剔掉**双腿高举 / 双腿绕颈**（那是仰躺的动作） |
| 站立类（站立后入 / 站立抱起） | 四肢着地、双腿绕颈 |
| 自慰 / 手交 / 指交 | **手腕束缚 / 手臂束缚**（要用手的活干不了） |
| 骑假阳具 / 自慰 | 女上位、男上位、跨坐（**单人**行为不需要伴侣） |

⚠️ 判据刻意**保守**：只收「物理上不可能同时成立」的。
`doggystyle` × `boy on top`（后入时男方也算上位）、`bent over` × 后入
（弯腰撅臀正是后入的姿态）这类**存疑的一律不判** —— 宁可少一条约束，
也不要误剔掉合理的组合。

### ② 表情配套：`emotion` × `eye_gaze` / `mouth`

原本三件套各抽各的，会出「**大笑 + 抿嘴**」（露齿大笑必然张嘴）、
「**哭泣 + 露齿笑**」、「**认真 + 伸舌**」这类打架组合。现在按一张矛盾矩阵收窄候选池：

| 情绪 | 剔掉的嘴部 / 眼神 |
|---|---|
| 大笑 / 傲娇嘟嘴 | 抿嘴、微张、咬唇、吐舌、张口 |
| 冷漠 / 认真 / 厌倦 | 露齿笑、吐舌、舔唇、单眼闭 |
| 难过 / 哭泣 / 含泪 | 露齿笑、单眼闭 |
| 厌恶 / 惊恐 / 困惑 | 露齿笑、舔唇 |
| 困倦 | 凝视、单眼闭 |

⚠️ 只**拦矛盾**，不做"风格偏好"（"得意该配什么眼神"是口味问题，不进表）——
所以同一情绪的配法依旧多样，不会千篇一律。

### ③ 场景倾向：`place` → 服装 / 姿势

按场景主题分七组（water / bed / school / daily / night / nature / city），
每组建两张表：

- **加权**（`THEME_WEIGHT`）：把该场景合理的选项权重放大（常态 ×4~10）。
  **不剥夺**其它选项 —— 泳池边照样可能抽到连衣裙（意外惊喜要留着）。
- **硬剔除**（`THEME_BAN`）：只剔**明确违和**的，如「泳池边 × 皮草大衣 / 和服」、
  「教室 × 极限泳装」。宁少勿多 —— 剔太多会让场景变成"只能出一种图"。

⚠️ 这套联动要求 `place` **先定下来**，而它原本排在服装/姿势**之后**的 ⑨ 场景段。
所以 draw 里对 `place` 做了**预抽**（`_one_pass` 开头的 `_pre_place`）：
与正式循环完全同构地抽一次，抽不中就不抽（联动自然退化成"无场景"，
与 v3.14.0 行为逐字一致）。

⚠️ **真机实测的边界**：场景搭配库的预设（`n_canon`）会**覆盖** place 与服装 ——
它是一键搭配，优先级更高。所以联动是"随机路径上生效"，
套用场景预设时以预设为准。

### 执行顺序（改这块前必读）

```
抽取时：bans_for() 收窄候选池（换掉矛盾项，保住内容）
   ↓
bias_for() 加权（场景倾向）
   ↓
apply_preset() 写入法典 / 场景预设的值
   ↓
sanitize() 再查一遍全部字段（清掉"事后才被改写"的矛盾）
   ↓
repair() 成品层复核（超档 / 结构互斥）
```
两条防线职责不同：抽取时的过滤是**重选**（保住内容），
sanitize 是**清空**（兜住预设/锁定/强制写入的那批）。
只留一条都会漏 —— `tests/check_v3_link.py` 两条都盯着。

## 四之九、服装智配与配色（v3.19.0）

两件事：**颜色可以落到具体单品上**，**服装之间不再互相打架**。

### 1. 两个独立颜色字段：`cloth_color` + `sock_color`

12 个色（`black / white / grey / red / orange / yellow / green / aqua /
blue / purple / pink / brown`），**分两条通道**（v3.20.0）：

| 字段 | 只管 | 用途 |
|---|---|---|
| `cloth_color` 服装颜色 | 下装 / 上装 / 整套 | 「红色裙子」「蓝色连衣裙」 |
| `sock_color` 袜子颜色 | 袜子 | 「紫色吊带袜」「红色过膝袜」 |

> ⚠️ 为什么必须分开：v3.19.0 只有 `cloth_color`，且把袜子放在第一个落点 ——
> 于是「紫色连衣裙」经常被抽成「紫袜子 + 素裙子」。袜子和裙子是两个独立
> 视觉块，硬塞同一个颜色反而不协调。现在想给袜子单独配色就填 `sock_color`，
> 两个都填就是「红袜 + 蓝裙」这种明确的双色搭配。

> ⚠️ 只有这 12 个是 danbooru 真实的基础颜色 tag。`navy blue / burgundy /
> dark green / beige / teal / lavender / champagne / silver` 实测
> **37/37 组合全失效**（没有 `navy_blue_thighhighs` 这种 tag），
> 留着它们等于让着色永远走"退化 = 不上色"，是假功能。

颜色**不单独输出**，而是拼进目标单品的第一个 tag：

| 抽取结果 | 成品 |
|---|---|
| 颜色`紫` + `thighhighs, garter straps` | `purple thighhighs, garter straps` |
| 颜色`红` + `skirt` | `red skirt` |
| 颜色`紫` + `black thighhighs` | 跳过（已自带颜色） |
| 颜色`紫` + `kneehighs` | 跳过，改试下一个部位（没有 `purple kneehighs` 这个 tag） |

落点优先级：`sock_color` 只落袜子；`cloth_color` 按 **下装 > 上装 > 整套**。组合是否有效由
`presets/anima_v4_color_matrix.json` 离线判定（safebooru post_count ≥ 30），
未命中就**不上色**并回显原因 —— 宁可没有颜色，也不吐无效 tag。

### 1.5 腿上词库（v3.20.0：34 → 66 条）

| 类别 | 新增 |
|---|---|
| 结构复合 | 吊带连裤袜 / 吊袜带连裤袜 / 过膝袜外穿连裤袜 / 袜上穿袜 / 多层腿装 |
| 图案材质 | 乳胶过膝袜 / 渐变过膝袜 / 珠光连裤袜 / 罗纹袜 / 渔网短袜 / 蕾丝短袜 |
| 破洞与连身 | 破洞过膝袜 / 连身网衣 / 渔网连身衣 / 黑色连身网衣（后三条 L2 起） |
| 非对称 | 不对称腿装 / 不配对腿装 |
| 装饰 | 蝴蝶结腿饰 / 缎带腿饰 |
| 日常 | 船袜 |
| 彩色固化 | 紫/红/蓝/粉 × 过膝袜 / 连裤袜 / 短袜（12 条） |

> ⚠️ 彩色固化只覆盖**能接颜色的三个基类**（thighhighs / pantyhose / socks）。
> 渔网、蕾丝、条纹、及膝、tabi 这些在 danbooru 里 **12 色组合全失效**
> （没有 `purple fishnet thighhighs` 这种 tag），所以它们只作为款式加入、
> 不带颜色变体 —— 图案款本身就自带视觉色。

### 2. 风格智配（控件 `outfit_style`）

| 取值 | 含义 |
|---|---|
| `随机`（默认） | 智配开，锚点自动：**场景 > 整套 > 上装 > 下装** |
| `不限` | 智配**整体关闭**，回到 v3.18 的纯随机（对照复现用） |
| 学院 / 职场 / 传统 / 运动 / 日常 / 居家 / 夜场 / 奇幻 / 泳装 | 整套服装**硬收敛**到该风格，其余部位软加权 |

九个风格组，每个服装选项按 1–2 组打标（`presets` 之外的
`anima_v4_outfit_style.STYLE_OF`，纯人工维护的语义知识）。

**三种作用力**：

1. **场景锚点** —— `poolside / beach / onsen` → 泳装，`classroom / library`
   → 学院，`bedroom / kitchen` → 居家，`office` → 职场……（`PLACE_STYLE`，
   只登记强关联的，其余不干预）。景和衣服对不上比"随机得不好看"更刺眼。
2. **软加权** —— 同风格 ×2.2，兼容组 ×0.4–0.85，不相干 ×0.35。软加权意味着
   「大概率合理、偶尔意外」，不是死板清单。
3. **硬铁律** —— 只收"穿在一起就是错的"：泳装 × 大衣/牛仔裤、婚纱 × 运动鞋、
   和服 × 高跟鞋、居家 × 高跟鞋……（`STYLE_BANS` / `ANCHOR_BANS`）。

**分层抑制**：整套服装抽到后，上装/下装的抽取概率 ×0.06 ——
否则会出「连衣裙 + 衬衫 + 长裤」三层叠穿。局部单品（`仅围裙 / 浴巾 /
缠胸布 / 仅比基尼上衣 / 寝间着`）不参与抑制。

### 3. 优先级（谁说了算）

```
forced（代码强制） > 锁定字段 > 控件 outfit_style > 场景锚点
> 整套服装自身 > 上装/下装 > 素随机
```

法典场景预设会显式写死服装，它优先级高于智配（用户主动套用），
但**低于 forced** —— v3.19.0 顺手修了这个既有缺陷
（之前 `forced place=poolside` 会被预设里的 `place=field` 盖掉）。

### 4. 验收

```bash
python tests/check_v3_color.py 40     # 智配 + 着色专项（30 条断言）
python tests/run_all.py 120           # 全套 21 项
```

## 四之十、角色官方发型对齐（v3.45.0）

控件 `hair_follow`（面板「发型对齐」勾选框，**默认开**）。与「外貌对齐」**互相独立**：
发色可以关着，只让发型跟着角色走。

| 项 | 行为 |
|---|---|
| 开 | 抽到单个角色时，按 `presets/char_hair_style.json` 写 `hair_len` / `hair_tie` / `hair_curl`，并把这三项加进 `trim_to_cap` 的保护集（爆 cap 时不会被削） |
| 关 | 一个字都不写，三项按权重与随机决定（与 v3.44.x 完全一致） |
| 多位角色 | 跳过（各有各的发型，对齐其中一个是错的） |
| 表里没有该角色 | 跳过并记 `_hair_style="nodata"`，发型交给随机 |
| 某字段权重设 0 | 该项让路（与外貌对齐同一条「显式 > 自动」纪律） |

数据文件：

```bash
python tools/derive_char_hair_style.py            # 从官方特征 tags 重新推导（会先备份）
python tools/derive_char_hair_style.py --check    # 只报告
python tests/check_v3_charhair.py                 # 专项基线
```

- 结构：`{"styles": {"<角色 tag>": {"hair_len": "...", "hair_tie": "...", "hair_curl": "..."}}}`
- **推不出来 / 拿不准的字段就不要写键** —— 空项 = 该子项继续随机，**绝不猜**。
- 表里出现词库外的词会被 `hair_style_for()` 直接丢弃（当作没有这一项），
  不会静默塞进正文；`check_v3_charhair.py` 会把这种情况判红。
- ⚠️ 表进进程缓存：改完文件**必须重启**后端。

## 五、三层权重

面板「设置 · 权重调节」区就是干这个的。数值范围 `0 – 3`：

| 层级 | 0 | 1.0（默认） | 3.0 | 中间值 |
|---|---|---|---|---|
| **段权重** | 整段关闭 | 正常 | 概率 ×3 | 相对倾向 |
| **字段权重** | 该字段永不出现 | 正常 | **必定出现** | 相对倾向 |
| **选项权重** | 该选项永不出现 | 正常 | 3 倍倾向 | 相对倾向 |

抽取概率：`p = clamp(基准概率 × 密度系数 × 段权重 × 字段权重, 0, 1)`

**「让某条选项一定有」的标准写法**：把该字段权重拉到 `3.0`（必现），
再在同字段的 🎯 细则里把其它选项设为 `0`。

三条硬规矩：

1. **权重改不了档位**。超档项即使权重给到 3.0 也进不来。
2. **权重 0 是强指令**。角色的官方发色对齐、法典场景填充都必须让路 ——
   否则用户看到的是「我明明关了，它还是出来了」。
3. **密度自适应会整体缩放基准概率**，但字段权重 3.0 短路成必抽、不受影响。

权重表存在节点控件 `weights_json` 里（跟着工作流走），格式：

```json
{
  "sections": {"hair": 0},
  "fields": {"hair_color": 3.0, "outfit": 0},
  "options": {"hair_color": {"white hair": 1, "black hair": 0}}
}
```

只写想调的部分即可。空串 / 非法 JSON / 类型不对 → 一律当默认，**不报错**；
但引用了不存在的段/字段/选项时会在报告里给告警（不报错是为了老工作流能跑，
给告警是为了用户知道权重没生效）。

## 六、随机规则

- **必填字段**永远抽；其余按基准概率抽（面板可调，默认 0.65，源脚本是写死的）。
- **🔒 锁定**：`lock_fields` 里的字段不参与随机，由上游给值。
- **互斥消解**：12 条 sanitize（全裸 × 具体服装、连裤袜 × 赤足、蒙眼 × 眼镜/心形瞳、
  背对 × 注视镜头、POV × 全身、低画质设备 × 专业景深、俯拍 × 向上看…）
  ＋ 6 组正则互斥。每条被清掉的都会写进报告，不静默。
- **标签数**：按人数取上限（单人 29 / 双人 37 / 复杂 45，来自源脚本），
  但**不是抽完硬削** —— 而是用**二分法调密度重抽**，让落点尽量进自检的合格区间。
  源脚本固定从 8 个软字段里删，实测一次能删掉 13 个字段（发型/脸型/气质全没），
  画面特色被削平而且自检照样红。
- **确定性**：`seed >= 0` 时逐字节可复现；派生种子一律走 `zlib.crc32`，
  **不用内置 `hash()`**（后者每进程加盐，可复现就成了空话）。
- **成品检查 + 自动修复**（v3.8.0，`repair()`）：`sanitize()` 看的是**字段**，
  管不到"绕过字段"的内容 —— 手写补句 `extra_body`、法典预设自带的 `n_extra`、
  锁定/强制指定的值、上游拼接台送进来的文本。`repair()` 看的是**成品标签串**，专治这一类：
  ① 超档标签剔除（已登记校准项除外）；② 六组结构互斥（数量/视角/眼罩/服装/设备景深/体位）；
  ③ 下划线归一 + 去重。修了什么都会写进报告（面板与 `report['repaired']` 都看得到）。
  ⚠️ 刻意**不修**：超长且不在词库内的标签（可能正是你手写的作品名）、标签数量（该调密度或上限）。
  ⚠️ 正常生成的正文**零改动**（`tests/check_v3_repair.py` 用 200 个样本钉住）——
  它是安全网，不是"顺手改用户内容"。
- **槽位序输出**：按 ANIMA3 v3.0 规范重排
  （人数 → 角色 → 外观 → 服装 → 姿势 → 表情 → 镜头 → 场景 → 光影 → 细节 → 自然语言），
  而不是按界面段序 —— 界面段序会把「服装状态」排在「场景」之后，进 CLIP 的顺序是错的。
- **自检 17 条致命项 + 10 条风格项**：标签数量 / 禁词 / 画师名 / 重复 / 人数一致性 /
  视角互斥 / 眼罩互斥 / 服装互斥 / 角色完整性 / 标签长度 / 标签格式 / 体位姿态 /
  **档位准入** / 槽位映射 / **判档一致性** …
  同一套判据也开放给第 4 个节点「Anima 提示词检查与修复（V4）」，
  可以对**任意**提示词（不只本插件生成的）跑一遍并自动修。

## 九、已知限制与待办

- **`wet hair` 的两难**：判定表的 `^wet ` 模式会把「湿发」判成 2 档。
  本插件用降级白名单把它放回 0 档（SFW 可用湿发），代价是约 19% 的 SFW 输出
  被造型台的 `grade_nsfw` 判成 2 档。**根因在判定表本身**，建议后续把
  `^wet ` 收窄成 `^wet (clothes|shirt|dress|...)`，改完重跑 `sync_nsfw_tables.py` 即可。
- `n_exposure / presenting`（翘臀展示）被判定表归进「性行为」分类 → 3 档。
  同一字段里其它 9 个选项都是 2 档，口径偏严。**未擅自降级**，留给用户决定。
- 源脚本 `face/eyes_color` 里「异色瞳」写了两遍（同一个 danbooru tag 出现两次），
  属源脚本小瑕疵，未擅自改（改了会破坏零漂移对拍）。
- 面板的「本段随机」目前只在后端支持，面板 UI 尚未挂按钮。
- **角色库中文名覆盖率 61%**：能自动提取的（wiki 别名里带中文的）已全部提取，
  剩下 39% 在 danbooru wiki 上确实没有中文别名，显示英文原名。
  想再提高需要手工补一张 `tag → 中文名` 表。
- **角色库不含男性，但可能有漏网**：性别判定优先级是
  「造型台全量性别表 > 官方特征 tags > wiki 代词 > 默认女性」。
  零人气（safebooru 上一条投稿都没有）**且没有任何女性佐证**的条目已剔除 105 条，
  但仍可能有边界情况；`tests/check_v3_chars.py` 会持续盯这条。
- **换装变体一并收录**：`asuna_(bunny)_(blue_archive)` 这类是独立的 danbooru
  角色 tag，在浏览器里作为不同的「造型版本」出现 —— 这是特性不是脏数据。
- **缩略图已在库内（2372/2383，覆盖 99.5%）**，缺的 11 位是**在 safebooru 上一条
  投稿都没有**的角色 tag（多为换装变体，如 `bb_swimsuit_mooncancer_fate`）——
  镜像上没人画过，所以确实没图可抓。这些角色在面板里退化成首字母色块，不影响使用。
  想补抓或重抓：
  `python_embeded/python.exe tools/fetch_character_thumbs.py`
  （**可中断可续跑**，每次跑都会先自愈清掉尺寸过小的坏图）。
- ⚠️ 抓图脚本必须用 **ComfyUI 内嵌的 Python**（`python_embeded`）—— 转 webp 依赖
  Pillow，系统 Python 里通常没有。
- **自定义角色没有发色 / 瞳色**（v3.4.0 的编辑弹窗刻意不暴露这两个字段）→
  `appearance_follow` 对它们会跳过对齐，不会报错，只是不强制发色瞳色。
  想补可以手改 `presets/user_characters.json` 里的 `hair` / `eyes`。
- **特征标签在引擎里只有两处被用到**（体型 + 兜底发色瞳色，见「四之五」）——
  改别的标签在当前版本不会影响出图，但会如实存下来（数据保真），
  将来引擎扩了用途就自动生效。
- ⚠️ **列表载荷的 `tags` 只带前 8 条**（卡片展示用）—— 想拿全量走
  `GET /characters/detail?tag=`。任何"想读全部标签"的新功能都别指望列表接口。
- **元数据里的"完整正向"是尽力还原**：`该流质量词 + 插件正文`。中间那段 **LoRA 触发词**
  由 LoraManager 运行时计算，插件无从得知，所以**不会出现在元数据里**（这是有意的取舍：
  宁可少一段，也不编一段假的）。原始正文另有 `anima_v4_prompt` 块的 `positive` 字段可对照。
- **兜底位填的是"正文原值"**，而那些位置运行时的真值由第三方给（如触发词）——
  本模块**只填空位**，绝不覆盖任何已有字面量；这些位置在 ComfyUI 界面里由插槽接管，不显示控件值。
- 看图工具读哪一份元数据（`workflow` 的哪个 widget、还是自定义键）由它自己决定，
  本插件把三类落点都写全以兼容；若某个工具仍读不到，需要拿它的解析逻辑单独适配。
- ⚠️ **手填角色（`force_role`）存的是 trigger 串** → 改过 trigger 的内置角色，
  老工作流里手填的那串会失配（**「已选角色」不受影响** —— 它存的是 tag）。
- ⚠️ **「视角」字段现在是分档字段**（v3.8.0）：段内混有 L0（`fisheye` 等）、
  L1（`pov breasts` / `pov legs`）、L2（`pov crotch`）、L3（`pov, fellatio` 等）。
  低档下这些高档选项**不会进入候选池**，面板上它们仍会列出来（标着 `L2` / `L3`），
  这是有意为之 —— 让你看得见"开高档能抽到什么"。段标题的「本档不参与」
  按"段内是否还有 ≤ 当前档的选项"判定，不会因为该段有高档选项就误标。
- ⚠️ **`first-person view` 这个标签在 danbooru 上并不存在**（源脚本原来就这么写，
  已与 `pov` 组合使用）。为了守住"词库零漂移"这条纪律**刻意保留原样**；
  真正起作用的是 `pov` 本身（danbooru 20 万+ 投稿）。新增的第一人称词条都用了
  真实存在的标签（已按 safebooru 的 `post_count` 逐个核对）。
- **`LEVEL_RAISE` 只覆盖判定表的盲区**，不是"我觉得该判几档"。
  能被判定表正确判定的（如 `pov, fellatio` 由 `fellatio` 判 3 档）**不重复登记** ——
  重复登记会让"判定表真源在造型台"这条纪律名存实亡。
- **场景搭配库目前 87 条**，档位分布 L0=32 · L1=2 · L2=8 · L3=36 · L4=9。
  ⚠️ **挖矿类（原自慰）做不出 L1**：擦边档不允许任何露出标签，而自慰的展示/行为标签
  （`n_state`/`n_exposure`/`n_body` 全部 L2、`n_act` 自慰项 L3、`squirting` L4）
